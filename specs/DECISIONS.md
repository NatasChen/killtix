# 實作決策紀錄

與 [客戶需求規格](customer_spec.md) 不同、或需要客戶確認的決策。每項都標示狀態。

| # | 主題 | 規格原文 | 實際做法 | 理由 | 狀態 |
| --- | --- | --- | --- | --- | --- |
| D1 | 預設管理員密碼 | 固定 `Admin@InitTemp2026!` | 帳號仍為 `admin@ticket.local`、強制改密；密碼由 `BOOTSTRAP_ADMIN_PASSWORD` 指定，未指定則首次啟動隨機產生並只在 log 顯示一次 | 固定密碼寫在公開文件中，每個部署都是已知憑證。若客戶堅持，設定 `BOOTSTRAP_ADMIN_PASSWORD=Admin@InitTemp2026!` 即完全符合原規格 | ⏳ 待客戶確認 |
| D2 | SSO（AD/LDAP/SAML/OIDC/SCIM）、FIDO2 | v1 必備 | 延至 v1.1；v0.1 提供本機帳號 + TOTP | 沒有實際 IdP 無法驗證；資料表已預留 `identity_provider` 欄位 | ⏳ 待客戶確認時程 |
| D3 | Cloudflare 部署（方案 B） | 雙軌並行 | 標示為實驗性、未實作，見 `deploy/cloudflare/README.md` | D1(SQLite)、SMTP、LDAP、bcrypt CPU 限制與現行架構差異大 | ⏳ 待客戶確認是否仍需要 |
| D4 | 改密前呼叫業務 API 的回應碼 | 原文件寫 `422`（或 403） | `403`，`code=password_change_required` | 語意上是「已認證但無權限」 | ✅ 已採用 |
| D5 | 「超過 3 天未結案」定義 | 原文件 SQL 與文字矛盾（`<=` vs 嚴格大於） | `status NOT IN (resolved, closed) AND created_at < now() - 72h`；剛好 72 小時不計入 | 與原文件文字一致；有邊界測試 | ✅ 已採用 |
| D6 | 附件上傳 | 原文件提及 | v0.1 未實作 | 需要儲存與病毒掃描設計 | ⏳ v1.1 |
| D7 | SLA 營業時間 | 原文件提及營業時間行事曆 | v0.1 以 24x7 計算；等待使用者期間暫停計時 | 營業時間/假日需另行設計 | ⏳ v1.1 |
| D8 | UI 視覺規範的套用方式（UI 重新設計第 1 批） | 客戶規格只要求 Light/Dark 主題與 WCAG AA，沒有指定色彩系統 | 依根目錄 `DESIGN.md` 套用設計 token，但只取風格：①`DESIGN.md` 只定義淺色，深色值由淺色推導並自行驗證 AA；②裝飾用的 sticker 色盤不進結構色，語意色（danger/warning/success、SLA、優先度 badge）維持獨立 CSS 變數；③hero、pricing 等行銷區塊不套用；④既有 CSS 變數名稱只增不改不刪（`tests/styles.test.ts` 依賴）；⑤若 `DESIGN.md` 的主色藍（#0075de）作為連結文字在暖白底上未達 4.5:1，新增較深的連結變數（如 `--accent-strong`）而不改 `--accent` 名稱 | 需求變更單明確要求依 `DESIGN.md` 重做樣式，但同時要求保留既有變數名稱與語意色；兩者只能靠「新增變數、不改名」調和 | ✅ 已採用；②的 sticker 色盤限制由 D9 放寬 |
| D9 | sticker 色盤與側邊欄色彩（UI 重新設計第 2 批） | `DESIGN.md` 規定介面只有黑白灰加一個藍，sticker 色盤只用於裝飾；深靛藍只用於單一 hero 區塊 | sticker 色盤（sky、purple、pink、orange、teal）可用於有意義的資料色：狀態 badge、儀表板色帶與長條圖、選單群組色塊；側邊欄使用深靛藍（`--nav-*`）。主要動作、連結與焦點仍只用主色藍；顏色都搭配文字標籤，不單靠顏色傳達 | 使用者認為介面過於單調；工單系統以資料為主，顏色帶有資訊（狀態、優先度、分類）比全部灰藍更好辨識。`DESIGN.md` 是行銷網站的風格參考，不改它，例外記在這裡與 AGENTS.md | ✅ 已採用 |
| D10 | UI 元件庫 | 原規格未指定；v0.3.0 前刻意不用 UI 套件，元件全部手刻在 `styles.css` | 維護者要求介面一律使用 Ant Design（antd 6）。顏色仍以 DESIGN.md 為準，集中在 `src/web/palette.ts`，以 theme token 傳給 antd；D8、D9 的色彩規則不變。antd 內建的少數文字（分頁、選單的 aria 標籤等）來自 antd 的 zh_TW / en_US 語系包，依使用者語系切換，是「所有可見文字走 glossary」的例外；空狀態與按鈕等可見文字仍走 glossary | 成熟的元件庫讓表格、表單、下拉選單與 RWD 一致且可及；CSP 已允許 inline style，antd 的 CSS-in-JS 不需放寬 CSP | ✅ 已採用 |
| D11 | 企業標誌的讀取路由不經 `guard()` | AGENTS.md 規則：新增路由一定要加 `guard()`，未完成改密／2FA 不能使用任何 API | `GET /api/v1/branding` 與 `/api/v1/branding/logo/{light|dark}` 不需登入；上傳與移除仍在 `/admin` 下，需要 `admin:settings`（只有系統管理員）。只接受 512 KB 以內的 PNG（檢查檔頭），不支援 SVG | 登入頁在登入前就要顯示標誌；標誌本來就是公開資訊，這兩個路由只回傳標誌。SVG 可以內含 script，改用 PNG 就不需要淨化 | ✅ 已採用 |
| D12 | 回覆不分對外與內部 | 原規格與 PRD FR-2.4：對話串區分對外回覆與內部備忘，內部備忘永不對申請人、廠商顯示 | 所有新回覆都公開給能看到工單的人；回覆者以「寄送 Email 通知」勾選框（預設勾選）決定是否通知對方。API 不再接受新的內部備忘（舊的 `type: "internal_note"` 回 400，避免舊畫面把內部內容誤發為公開回覆）；已存在的內部備忘維持只有內部人員可見。`visibility='internal'` 的自訂欄位與系統事件不受影響 | 維護者要求：實際使用上不需要區分，回覆者只需要決定是否寄送通知 | ✅ 已採用 |
| D13 | 郵件設定存在資料庫、預設沿用環境變數 | 原規格（PRD FR-4.2、FR-6.1）只把 SMTP 設定列為環境變數，寄信方式固定為 SMTP | 寄信方式存在 `system_settings`，預設 `env`（沿用 `SMTP_*`，既有部署升級後不需設定）；可改為 `smtp`（介面填寫）或 `resend`（HTTP API，`fetch` 呼叫 `POST https://api.resend.com/emails`，不新增套件）。寄信時依目前設定決定，儲存後立即生效、不需重新啟動；Telegram／Teams 仍只由環境變數設定。SMTP 密碼與 Resend API Key 以 `deps.secretBox` 加密儲存，只寫不讀（回應只給 `hasPassword`），留空儲存表示不變更，解密失敗視為未設定並提示重新輸入。沒有新增環境變數、沒有部署變更 | 維護者要求改寄信方式不必重新部署，並新增 Resend 作為第二種寄信方式；同時要求既有部署升級後行為不變，因此預設值必須是 `env`。秘密只寫不讀沿用既有 `secretBox`（2FA 金鑰同一機制） | ✅ 已採用 |
| D14 | 使用者可屬於多個團隊、`users.team_id` 暫時保留 | 原規格（PRD §7.1）只有 `users` 與 `teams`，隱含一位使用者屬於一個團隊（`users.team_id`） | 新增 `team_members`（`team_id`、`user_id`，複合主鍵，皆 `on delete cascade`）作為使用者與團隊的多對多關聯；`users.team_id` 保留但不再使用，下一版移除。升級時在 `db/seed.ts` 一次性把 `users.team_id` 有值的使用者回填到 `team_members`，完成後在 `system_settings` 記錄 `migrations.team_members_backfilled`，之後啟動不再執行（AGENTS.md 規則 8：不可覆寫管理員已做的成員異動）。使用者 API 的團隊欄位由 `teamId` 改為 `teamIds: number[]`（破壞性變更，前端同步）。可見範圍：有 `ticket:read:team` 者看得到自己任一團隊的工單（查詢層 `exists` 子查詢）；`vendor`／`end_user` 即使被加入團隊仍只看被指派、自己開立或被加入關注的工單 | 需求變更單要求同一團隊成員共同處理並由其中一人認領；保留欄位是為了讓升級不遺失資料、必要時可回退，移除留到下一版 | ⏳ 待客戶確認（`users.team_id` 於下一版移除） |
